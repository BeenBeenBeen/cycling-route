# 成都周边骑行路线小红书发布工具 V2.0 需求方案

## 1. 项目概述

V2.0 在 V1 的小红书内容生成、封面海报、Markdown 保存和辅助发布能力基础上，新增“起点和终点驱动的路线生成”工作流。用户不再需要手工填写完整路线事实，只需要输入起点和终点文本，系统通过高德地图解析地点、生成骑行路线，并生成可导入 Strava 的 GPX 路书。

V2.0 重点解决四件事：

- 降低骑行路线内容创作和路线规划成本。
- 通过高德地图生成真实骑行路线，减少手工填写路线事实。
- 自动生成 Strava 可导入 GPX 路书，便于骑行前使用。
- 保留人工确认机制，避免 AI 或地图服务生成的内容未经审核直接发布。

## 2. V2.0 产品范围

V2.0 包括：

- 顶部导航栏，将“路线规划”和“小红书发布”拆成两个割裂界面。
- 路线规划界面采用地图优先的工具型布局，参考 Strava 路线创建页的交互方向。
- 小红书发布界面采用内容编辑工作台布局，专注文案、封面、Markdown 和发布辅助。
- 路线规划界面的输出可以作为小红书发布界面的输入。
- 起点文本和终点文本输入。
- 高德地点候选查询，用户确认具体起点和终点。
- 高德骑行路径规划。
- 页面交互式路线图展示真实路线。
- 路线事实生成，包括距离、预计耗时、起点、终点、路线 polyline、累计爬升。
- 高德 `GCJ-02` 坐标转换为 `WGS84`。
- Open-Elevation 批量查询海拔。
- 按路线距离每 `100m` 采样并计算累计爬升。
- 用户人工确认或修正累计爬升。
- 生成 Strava 可导入 GPX 路书。
- GPX 保存到 `data/routes/*.gpx`。
- 页面提供 GPX 下载按钮。
- Markdown 中记录 GPX 文件路径和路线事实。
- 封面海报叠加路线线条、里程、爬升、起终点等事实信息。
- AI 自动补全路线亮点、风险提醒、补给点、适合人群、拍照点等内容。
- 所有 AI 补全内容必须人工确认和编辑。
- 保留小红书文案生成、封面生成、Markdown 保存和 Playwright 辅助发布。

V2.0 暂不包括：

- 途经点规划。
- 全自动发布。
- 手机端发布自动化。
- 路线规划偏好配置，例如避开大路、优先绿道、最少爬升。
- 多路线候选比较。
- 实时路况验证。
- Strava API 自动上传。
- 多账号发布。
- 定时发布。
- 数据分析或互动表现追踪。

## 3. 用户流程

1. 用户打开本地 Web 应用。
2. 用户通过顶部导航进入“路线规划”界面。
3. 用户输入起点文本和终点文本。
4. 系统调用高德地点候选接口。
5. 用户从候选列表中确认具体起点和终点。
6. 用户点击“生成骑行路线”。
7. 系统调用高德骑行路径规划接口。
8. 系统在地图主界面展示交互式高德路线图。
9. 系统抽取路线 polyline、距离、预计耗时等路线事实。
10. 系统将路线坐标从 `GCJ-02` 转换为 `WGS84`。
11. 系统按路线距离每 `100m` 采样。
12. 系统批量调用 Open-Elevation 查询海拔。
13. 系统计算累计爬升。
14. 用户确认或修正累计爬升。
15. 系统生成 Strava 可导入 GPX。
16. 用户可以下载 GPX。
17. 用户点击“发送到小红书发布”。
18. 系统保存当前路线数据包并跳转到“小红书发布”界面。
19. 系统将路线事实填入小红书发布表单。
20. 用户编辑或补充发布所需的路线事实。
21. 系统基于路线事实和 AI 补全内容生成小红书文案。
22. 用户编辑并确认小红书内容。
23. 用户生成封面海报。
24. 系统将路线线条和路线事实叠加到封面图。
25. 用户保存 Markdown。
26. 用户启动小红书辅助发布。
27. 系统打开小红书发布页，上传封面并填写标题、正文和标签。
28. 用户人工完成登录、验证码、内容检查和最终发布。

## 4. 前端 GUI 与页面结构

### 4.1 顶部导航栏

V2.0 必须提供顶部导航栏，将主要工作流拆成两个清晰入口：

- 路线规划。
- 小红书发布。

导航栏要求：

- 在两个界面中常驻。
- 当前界面必须有明确高亮状态。
- 后续可以扩展“历史路线”“草稿箱”“配置”等入口。
- 不把路线规划控件和小红书发布控件混在同一个工作区中。

### 4.2 路线规划界面

路线规划界面参考 Strava 路线创建页，采用“地图优先”的工具型布局。地图是第一视觉和主要操作区域，表单和路线摘要以浮层方式附着在地图上，而不是传统上下堆叠表单页。

路线规划界面包含：

- 全屏或近全屏地图主区域。
- 左侧浮层路线面板。
- 底部路线摘要条。
- 右上角地图和路线操作区。

左侧路线面板包含：

- 起点输入。
- 终点输入。
- 城市输入，如果需要。
- 地点候选查询。
- 起点候选确认。
- 终点候选确认。
- 生成骑行路线按钮。

地图主区域要求：

- 默认定位成都周边。
- 生成路线前显示地图空状态或基础地图。
- 生成路线后显示高德骑行路线 polyline。
- 后续预留骑行热力图、图层切换、路面类型、爬升剖面等扩展位。

底部路线摘要条包含：

- 距离。
- 累计爬升。
- 预计耗时。
- GPX 状态。
- GPX 下载入口。

右上角操作区包含：

- 重新规划。
- 生成 GPX。
- 发送到小红书发布。

### 4.3 小红书发布界面

小红书发布界面采用内容编辑工作台布局，不承担路线搜索和地图规划职责。

小红书发布界面包含：

- 路线事实表单。
- 小红书文案生成入口。
- 小红书文案编辑器。
- 标题候选选择。
- 封面图生成入口。
- 封面预览。
- Markdown 保存入口。
- 小红书辅助发布入口。

小红书发布界面必须能接收路线规划界面的输出。接收后，系统应将 `plannedRoute.routeFacts` 填入路线事实表单，并携带 `gpxPath`、`gpxUrl`，用于 Markdown 保存和后续发布资料整理。

### 4.4 界面数据交接

路线规划界面向小红书发布界面交接的数据包定义为：

```ts
type RoutePublishDraft = {
  plannedRoute: PlannedRoute;
  routeFacts: RouteInput;
  gpxPath?: string;
  gpxUrl?: string;
  updatedAt: string;
};
```

交接要求：

- 用户必须通过明确动作“发送到小红书发布”触发交接。
- 交接后跳转到“小红书发布”界面。
- 推荐使用 `localStorage` 保存最近一次路线发布草稿，避免刷新页面后丢失。
- 如果小红书发布界面已有用户编辑内容，系统不得静默覆盖，应提示用户确认或保留当前编辑内容。

## 5. 输入和确认

### 5.1 用户输入

V2.0 初始输入只包含：

- 起点文本。
- 终点文本。

### 5.2 地点候选确认

系统必须展示高德返回的起点候选和终点候选，用户确认后才能规划路线。

候选信息至少包含：

- 地点名称。
- 地址或区县信息。
- 经纬度。
- 高德 POI ID，如果接口返回。

如果候选为空，前端必须提示用户调整关键词。

## 6. 路线规划

路线规划使用高德地图骑行路径规划。

输入：

- 起点候选坐标。
- 终点候选坐标。

输出：

- 路线距离。
- 预计骑行耗时。
- 路线 polyline。
- 路线步骤，如果高德返回。
- 起点和终点坐标。

V2.0 暂不支持途经点。后续如果支持途经点，应优先确认高德骑行接口是否原生支持；如果不支持，再评估分段规划与路线拼接。

## 7. 坐标系统

高德返回坐标按 `GCJ-02` 处理。

GPX 和 Strava 导入按 `WGS84` 处理。

系统必须在生成 GPX 前执行：

```text
GCJ-02 -> WGS84
```

页面上的高德地图展示可以继续使用高德坐标，不要求转换。

## 8. 海拔和累计爬升

海拔服务使用公共 Open-Elevation API。

### 8.1 采样规则

- 不逐点查询高德 polyline 中的所有点。
- 按路线距离采样，默认每 `100m` 一个点。
- 必须使用批量查询接口，减少调用次数。
- 单批点数建议默认最多 `100` 个。
- 路线较长时分批查询。

### 8.2 累计爬升计算

系统基于采样点海拔计算累计爬升：

- 只累计正向海拔变化。
- 需要过滤海拔噪声。
- 默认噪声阈值建议为 `3m`。
- 低于阈值的连续小幅变化不计入累计爬升。
- 累计爬升是沿路线采样点逐段累加的正向爬升，不是终点海拔减起点海拔。

### 8.3 人工修正

系统自动计算 `elevationGainM` 后，必须允许用户人工修正。

最终用于文案、封面、Markdown 和 GPX 元数据的累计爬升，以用户确认后的值为准。

### 8.4 失败兜底

如果 Open-Elevation 调用失败：

- 路线和 GPX 仍可生成。
- 用户必须可以手工填写累计爬升。
- GPX 可以不包含 `<ele>`，但仍应保持 Strava 可导入。

## 9. GPX 路书

系统必须生成 Strava 可导入 GPX。

GPX 要求：

- 使用 `WGS84` 坐标。
- 包含完整 track。
- 包含路线名称。
- 海拔查询成功时，track point 包含 `<ele>`。
- 海拔查询失败时，可以不包含 `<ele>`。
- 文件保存到 `data/routes/*.gpx`。
- 页面提供下载按钮。
- Markdown 中记录 GPX 文件路径。

文件名规则建议：

```text
YYYY-MM-DD-HHmm-<start>-to-<end>.gpx
```

同一分钟内重复生成时，不得覆盖旧文件，应自动追加序号。

## 10. AI 内容补全

V2.0 中，AI 可以基于路线事实自动补全：

- 路线亮点。
- 风险提醒。
- 补给点。
- 适合人群。
- 推荐出发时间。
- 拍照点。
- 美食推荐。
- 小红书标题、正文、攻略、彩蛋、话题标签。
- 封面主标题、封面副标题、图片提示词。

约束：

- 距离、耗时、起点、终点、路线轨迹来自高德，不由 AI 编造。
- 累计爬升来自 Open-Elevation 自动计算和用户确认，不由 AI 编造。
- AI 补全内容必须可编辑。
- AI 补全的补给点、拍照点、美食推荐如果不是用户确认事实，必须使用“可探索”“可留意”“建议提前确认”等表达。
- 禁止将 AI 猜测内容当作确定事实发布。

## 11. 封面海报

V2.0 保留封面海报生成能力，并新增路线线条叠加。

封面视觉风格参考用户提供的骑行俱乐部小红书海报样张，整体方向为“全屏实拍旅行海报 + 俱乐部活动视觉”，而不是抽象地图或数据卡片风格。

封面包含：

- AI 生成的全屏实拍感骑行海报背景。
- 本地渲染的路线线条。
- 路线名称。
- 起点和终点。
- 距离。
- 累计爬升。
- 难度或路线类型，如果用户确认。

背景生成风格要求：

- 竖版全屏背景，不使用边框和卡片容器。
- 画面应有真实摄影感，可包含山路、海岸公路、森林公路、远山、骑行者剪影、骑行队伍、晨昏光影、雾气、动感模糊或强烈阴影。
- 保留大块干净区域，便于本地叠加白色大标题和路线数据。
- 色彩可以使用暖金、深蓝、森林绿、海岸蓝、暗棕等户外运动色调。
- 可使用胶片颗粒、光晕、笔刷动势、轻微拼贴感，形成小红书骑行俱乐部活动海报质感。
- 不生成地图、路线轨迹、等高线、地理纹理、UI 元素、logo、水印、可读文字或数字。

本地叠加风格要求：

- 使用白色大标题直接压在画面上，不使用深色信息卡片。
- 顶部保留小型俱乐部/路线标识区。
- 中部可叠加手绘感路线线条或笔刷线。
- 底部叠加里程、爬升、起终点等路线事实。
- 所有中文文字、关键数字、路线线条必须由本地程序渲染。

图片模型仍不负责生成最终中文文字、关键数字、logo 和路线线条。

最终海报尺寸：

```text
1080x1440
```

背景生成默认尺寸：

```text
1024x1536
```

Markdown 必须包含：

- 起点和终点。
- 高德候选确认信息。
- 路线距离。
- 预计耗时。
- 累计爬升。
- GPX 文件路径。
- 选定标题。
- 小红书正文。
- 路线攻略。
- 路线彩蛋。
- 话题标签。
- 封面标题。
- 封面副标题。
- 图片提示词。
- 封面海报文件路径。
- 生成时间。

## 13. 发布辅助

V2.0 继续使用 Playwright 辅助小红书桌面端发布。

发布辅助能力：

- 打开小红书发布入口。
- 上传生成的封面海报。
- 填入选定标题。
- 填入正文。
- 填入话题标签。
- 停留在最终发布前。

系统仍禁止：

- 绕过登录或验证码。
- 保存小红书账号密码。
- 自动点击最终发布。
- 规避平台限流、风控或反滥用机制。

## 14. API 范围

V2.0 建议新增 API：

- `POST /api/search-places`：根据起点或终点文本查询高德地点候选。
- `POST /api/generate-route`：根据确认后的起点和终点生成骑行路线。
- `POST /api/generate-gpx`：根据路线生成 Strava 可导入 GPX。
- `GET /media/routes/:filename`：下载 GPX 文件。

V2.0 保留 API：

- `GET /api/health`
- `POST /api/generate-post`
- `POST /api/generate-cover`
- `POST /api/save-markdown`
- `POST /api/assist-publish`

## 15. 配置项

V2.0 新增配置：

| 变量 | 必填 | 说明 |
|---|---:|---|
| `AMAP_API_KEY` | 是 | 高德 Web 服务 API key |
| `AMAP_JS_API_KEY` | 是 | 高德 JS 地图 key，用于服务端配置检查和前端配置对齐 |
| `VITE_AMAP_JS_API_KEY` | 是 | 暴露给前端的高德 JS 地图 key，用于地图展示 |
| `VITE_AMAP_SECURITY_JS_CODE` | 是 | 高德 JS API 安全密钥，用于前端地图加载 |
| `OPEN_ELEVATION_BASE_URL` | 否 | Open-Elevation 地址，默认公共 API |
| `ELEVATION_SAMPLE_INTERVAL_M` | 否 | 海拔采样间隔，默认 `100` |
| `ELEVATION_BATCH_SIZE` | 否 | Open-Elevation 单批查询点数，默认 `100` |
| `ELEVATION_GAIN_NOISE_THRESHOLD_M` | 否 | 累计爬升噪声阈值，默认 `3` |

V1 既有配置继续保留，包括 DuckCoding 文案和图片 key、小红书发布入口、代理、日志级别。

## 16. 日志和安全

日志必须继续使用 JSON Lines。

必须记录：

- 地点候选查询开始、完成、失败。
- 路线规划开始、完成、失败。
- Open-Elevation 批量查询开始、完成、失败。
- GPX 生成完成或失败。
- API 请求和响应摘要。

必须脱敏：

- `AMAP_API_KEY`
- `AMAP_JS_API_KEY`
- `VITE_AMAP_JS_API_KEY`
- `VITE_AMAP_SECURITY_JS_CODE`
- `DUCKCODING_TEXT_API_KEY`
- `DUCKCODING_IMAGE_API_KEY`
- authorization
- cookie
- token
- secret
- 验证码

禁止记录：

- 图片 base64。
- 账号密码。
- 小红书 cookie。

## 17. 验收标准

- 用户只输入起点和终点文本即可开始路线生成。
- 系统提供顶部导航栏，并将“路线规划”和“小红书发布”拆成两个割裂界面。
- 路线规划界面采用地图优先布局，地图是第一视觉和主要操作区。
- 小红书发布界面只承担内容编辑、封面生成、Markdown 保存和辅助发布。
- 系统展示高德地点候选，用户可以确认具体起终点。
- 系统可以生成骑行路线并在页面地图上展示。
- 系统可以根据路线生成距离和预计耗时。
- 系统可以按每 `100m` 采样并批量调用 Open-Elevation。
- 系统可以自动计算累计爬升，并允许用户修正。
- 系统可以生成 Strava 可导入 GPX。
- 页面提供 GPX 下载按钮。
- 用户可以将路线规划结果发送到小红书发布界面。
- 小红书发布界面可以读取路线规划输出并填充路线事实表单。
- Markdown 包含 GPX 路径和路线事实。
- 封面海报包含路线线条、里程、爬升、起终点。
- AI 补全内容必须可编辑和人工确认。
- 系统可以继续保存 Markdown 和辅助发布小红书。
- 系统不会自动点击最终发布按钮。
